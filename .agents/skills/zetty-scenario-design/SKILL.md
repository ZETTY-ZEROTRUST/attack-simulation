# 사례 기반 시나리오 설계

현재 세션의 최신 사용자 지시를 우선하고 작업에 필요한 owner만 읽는다. 시나리오 owner는 attack-simulation/README.md, 이벤트 계약은 log-pipeline/contracts/README.md다. 삭제된 루트 문서나 이전 학습 자료는 복원하지 않는다. 저장소 경로는 루트 기준이다.

## 문제를 먼저 고정

- 업무 주체·보호할 정보·허용된 업무·공격자가 가진 권한과 접근 경로를 명시한다. 직원 업무 계정은 현재 고객 본인 소유권 모델과 다르며, 채택 전에는 구현된 기능으로 쓰지 않는다.
- 인증 실패, 명시적 인가 위반, 권한 안의 행동 악용, 회수 후 재사용을 구분한다. AI의 역할은 관측 가능한 행동의 위험 평가다. 내심의 악의·탈취 사실을 관측 없이 정답으로 요구하지 않는다.
- 현재 README의 네 시나리오 → 관측 가능성 → Jev 입력·평가·보고서 → 구현 순서로 구체화한다. backend 목표는 Trust Chain 계층과 세 실행 앱이며, 전체 코드를 즉시 재작성하라는 뜻이 아니다.

## 근거와 시나리오 카드

공식 사고 조사·제재문, KISA/금융보안원 자료, 원 논문을 우선하고 URL·발행일·해당 절을 확인한다. 가이드의 결함 예시와 실제 사고, 합성 dataset을 구별한다. 사건에서 확인되지 않은 속도·토큰 방식·공격 절차를 사실로 추가하지 않는다.

시나리오마다 다음을 작성한다.

- ID·상태(제안/구현/실행)·출처와 확인된 사실·로컬 적용 시 달라진 가정.
- 공격자 초기 권한·목표·전제·행동 순서·예상 HTTP 결과.
- 정상 반례·서버가 측정할 신호·수집 위치·누락 처리·분석 시점.
- 서버 차단 기준, AI 판정 기대와 유보 조건, 대응·해제·감사 기준을 각각 명시.
- 실행 요청이 있으면 target allowlist·모의 계정·요청량·기간·timeout·종료 조건·정리 범위.

## 평가의 함정

- 정상 집중 조회·승인 작업·신규 담당자·시간대 변화와 저속 누적 수집을 포함한다. 요청량만으로 정답이 결정되는 자료에 한정하지 않는다.
- 서버의 담당 범위·승인은 시점이 있는 신뢰 데이터다. 클라이언트의 정상 선언과 나중 조사한 공격자 정보를 입력으로 쓰지 않는다.
- 같은 관측에 다른 정답이 붙는 쌍은 식별 불가능한 한계 사례로 남긴다. 공격 역할·계정 ID·시나리오명을 단서로 넣어 구분을 만들어내지 않는다.
- 기존 start/S1~S4 번호를 현재 네 시나리오나 실행 완료 결과로 재사용하지 않는다. 과거 runner·학습 결과는 삭제되었으므로 존재한다고 가정하거나 복원하지 않는다.

조사·설계 요청은 실행 권한이 아니다. 문서에서는 실제 실행 결과와 제안된 기대값을 구분한다.
