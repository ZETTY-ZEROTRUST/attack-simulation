# S-00 공격 → 방어 → 부하 개선 로드맵

- 상태: 기준 문서
- 작성/갱신: 2026-09-27

## 전체 그림

왼쪽 "공격", 오른쪽 "방어 도입". 위에서 아래로 방어가 인증 계층 바깥으로 넓어진다.
기본기(B0)는 갖췄다고 가정하고, 그래도 남는 구멍을 순서대로 메운다.

```
        공격                                    방어 도입
┌───────────────────────────────────────────────────────────┐
│ B0  표준 구현 (출발점, 공격/방어 공통)                       │
│     RS256·알고리즘 고정 / AT(메모리) / RT(HttpOnly 쿠키)     │
│     / RBAC / 401·403 구분                                    │
└───────────────────────────────────────────────────────────┘
  S1  남의 주문 ID 조회 (BOLA)      →   객체 단위 소유권 검사
  S2  탈취 토큰 계속 사용            →   RT Rotation·재사용 감지·폐기
  S3  서명키 유출로 토큰 위조        →   발급 대장 대조 + 주체(회원) 검증
  S4  인증 통과 후 이상 사용         ┈▶  행위 기반 탐지·대응 (막기가 아니라 잡기)
```

- S1~S3의 방어는 **차단**이다. S4는 **탐지**라서 점선으로 구분한다(모델은 Codex 담당).
- 방어가 인가(S1) → 토큰 회수(S2) → 발급 기록(S3) → 행위 감시(S4)로 넓어진다.

## 각 단계 문서가 반드시 담을 것

STAR + 부하 + 근거. 저장소별 `docs/star/`에 단계마다 문서 하나.

1. **공격 (S)**: 재현 방법, 성공(취약) 증거 — run_id·응답 코드·건수.
2. **왜 막나 (T)**: 금융 관점 리스크와 차단 기준.
3. **방어 구현 (A)**: 무엇을 고쳤나.
4. **기술 선택 이유·대안 비교 (A 필수)**: 왜 이 방식인가. 후보와 트레이드오프를 표로.
   - 예: RT 저장을 BFF vault vs 브라우저 HttpOnly 쿠키, 폐기 확인을 매 요청 DB vs Redis 캐시.
5. **재공격 (R)**: 같은 시나리오로 다시 쳐서 차단율·정상 요청 성공률.
6. **부하 테스트 (R)**: 방어 도입 전/후 처리량·p95/p99·에러율. 병목 원인(풀·스레드·쿼리)과 개선.
7. **개선 후 재측정 (R)**: 같은 조건에서 수치. 3회 중앙값·환경·분모 명시.

수치는 실측만. 토큰·키 원문은 기록하지 않는다. 목표치와 실제값을 구분한다.

## 맞춰야 할 결정

- B0의 웹 토큰 보관 모델: 이 로드맵 그림은 **AT 메모리 + RT HttpOnly 쿠키**다. 반면 인증 owner 문서(`backend/docs/auth-token-architecture.md`)의 채택안은 **BFF vault**다. 둘은 S2 방어의 형태를 바꾼다. 어느 쪽을 B0로 둘지 S2 착수 전에 owner 문서와 함께 확정한다(자소서 서술은 그림 기준, 구현 계약은 owner 기준 — 충돌 시 owner 갱신).
