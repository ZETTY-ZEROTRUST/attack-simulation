# L-05 로그인 처리량 병목 — BCrypt vs KMS 서명 vs DB

- 상태: 계획
- 연결: 부하 L-1(최초 발견: knee가 로그인 경로) · backend auth-server
- 작성/갱신: 2026-09-27

## S — 문제

- L-1 기준선에서 전체 p95 5.9초의 원인이 로그인 경로였다(마이페이지 p95는 11ms).
- 로그인 1건 = 사용자 조회 → **BCrypt 비밀번호 검증** → **KMS Sign(RS256, 네트워크 왕복)** → 발급대장 INSERT → RT INSERT.
- 어느 단계가 병목인지 모르면 개선 방향(서명 방식 교체, BCrypt 비용 조정, 스케일 아웃, 요청 제한)을 고를 수 없다.

## T — 목표

- 로그인의 포화점(knee)과 그때 **어느 컨테이너의 CPU가 먼저 한계에 닿는지** 확인해 병목을 특정한다.
- 성공 기준: 같은 조건에서 병목 단계를 수치로 지목(컨테이너 CPU 사용률·상한 대비 비율, 단계별 비용)하고, 개선안별 전후 로그인 TPS·p95를 측정한다.

## A — 어떻게

### 계획
1. `constant-arrival-rate`로 `POST /auth/login`만 부하(사용자 순환, 반복당 1건), 단계 부하로 knee 탐색.
2. 같은 구간의 컨테이너 CPU(cAdvisor): `auth`(상한 2코어), `kms`(상한 0.5코어), `mysql`.
3. 가설 검증
   - BCrypt(cost 10)는 요청당 수십 ms의 CPU → auth CPU가 먼저 포화되면 BCrypt 병목
   - kms CPU가 상한(0.5)에 붙으면 서명 병목(로컬 에뮬레이터 수치이며 실제 AWS KMS 성능이 아님)
4. 병목에 맞춘 개선안을 하나씩 적용해 재측정.

### 개선 후보와 판단 기준 (측정 후 확정)
| 후보 | 효과 | 보안 영향 |
|---|---|---|
| BCrypt cost 낮추기 | CPU↓ | **무차별 대입 저항 약화** → 근거 없이는 하지 않음 |
| auth 인스턴스·CPU 증설 | 선형 확장 | 없음(비용) |
| 서명 in-process(파일 키) | 네트워크 왕복 제거 | 개인키가 앱 메모리에 존재 → KMS 모델과 다름. 비교용으로만 |
| 로그인 요청 제한(rate limit) | 과부하·대입 공격 동시 방어 | 긍정적 |
